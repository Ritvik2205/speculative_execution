**Follow-up (corpus regeneration, this session): done.** Confirmed the scope precisely: 488/498 (98%) of `riscv_corpus/*.s` files **fail to actually assemble** (`riscv64-elf-gcc -c` errors: `unrecognized opcode`) — the original pipeline used `gcc -S` and never invoked the assembler. Root cause: 139 C source files under `c_vulns/c_code/**` contain `__asm__` blocks written in literal ARM64 or x86 AT&T syntax (inline asm is opaque to the compiler backend, copied verbatim regardless of compile target). Catalogued every distinct inline-asm statement actually used (2081 blocks in `.c` sources, 1564 corresponding `#APP` blocks in the compiled `.s` output → reduces to ~20 real primitives via line-level pattern matching).

Two implementation attempts:
1. **Patch `.c` sources + recompile** (as originally planned) — blocked: the sources need a full hosted libc (`stdio.h`, `setjmp.h`, `signal.h`, `sys/mman.h`, `x86intrin.h`, etc.) that the bare-metal `riscv64-elf-gcc` toolchain doesn't provide, and no stub headers survived from however the corpus was originally generated. Still built `scripts/translate_riscv_inline_asm.py` for this (useful for documentation/future use, `#if defined(__riscv)` branches, x86/ARM path untouched) — 1842/2283 blocks + 215 special-cased `rdtsc` translations, 1 flagged (a rare x86 flags-based mask trick, correctly left for manual review).
2. **Patch the already-compiled `.s` files' `#APP` blocks directly** (pivoted to this) — sidesteps the missing-libc problem entirely, since assembling a `.s` file needs no C headers (already proven — that's how the 98% failure count was measured). `scripts/patch_riscv_corpus_asm.py` reuses the same translation table. **Result: 1564/1564 (100%) blocks translated, then validated by actually invoking the assembler: 498/498 (100%) files now assemble clean** (one extra fix needed along the way: `cbo.inval`/`cbo.flush` require the Zicbom extension declared in the file's own `.attribute arch` string, or the in-file directive overrides any `-march` flag on the command line).

One known, accepted limitation: GCC's x86 `rdtsc`-based timing helper uses register CONSTRAINT LETTERS (`"=a"`/`"=d"`) meaningless for the RISC-V backend — by the time it reaches the compiled `.s`, GCC has already silently compiled it away into a constant (`li a5,0`), with no `#APP` block or original text left to translate. This is invisible to SpecDiscover's classifier, though: it's a purely static analyzer (never executes anything), so a semantically-broken timing measurement doesn't affect classification — what matters is the actual leak-mechanism instructions (loads/shifts/cache-ops), which do survive as translatable text and are what this fix addresses.

**End result, re-scored on the regenerated corpus:** RISC-V zero-shot accuracy 34.48% (latest single checkpoint), **L1TF recall 0.00%→37%, MDS 0%→11%**, and `CACHE_TEMPORAL`/`FENCE_BOUNDARY` edges — both exactly 0 before — now appear (0.9%/1.7% of edges). Multi-seed check on 5 older (pre-store-transmitter-fix, pre-ARCH_VOCAB-fix) checkpoints shows L1TF recall `[4.9%, 0%, 0%, 0%, 42.0%]` (mean 9.4%) — the corpus fix removed the *structural* impossibility (0.00% every single time, no exceptions, confirmed earlier) but RISC-V zero-shot transfer remains inherently high-variance (untrained arch-embedding, no RISC-V training data exists at all). Honest framing: this is a real, large, mechanism-attributable improvement, not a claim that RISC-V detection is now reliable.

## 4. Out of scope / structural

No component of SpecDiscover — classifier, spec engine, or generator — is ever
checked against actual speculative-execution behavior. Every "ground truth" in
the system is one of: (a) the hand-written rules themselves, (b) an independent
*syntactic* oracle (llvm-mc/capstone, which knows instruction encoding but not
security semantics), or (c) another learned model. Closing this (G10) requires
a real simulator-in-the-loop oracle (gem5 or similar) — already scoped as
Phase 4 in the project roadmap, and correctly left there. This audit does not
attempt to build that oracle; it only makes sure every claim that *doesn't*
require it is checked as rigorously as it can be, and every claim that *does*
require it is labeled as unverified rather than implied to be settled.
