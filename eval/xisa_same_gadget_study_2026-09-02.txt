CROSS-ISA STUDY: same attack source compiled to x86 / arm64 / riscv64 (2026-09-02)
==================================================================================
One minimal gadget SOURCE per class, compiled to all 3 ISAs (clang x86/arm,
riscv64-elf-gcc). Same semantics, different codegen. Baseline classifier v54_spec
(NO riscv training). qemu_data/xisa/, reproduce with the .c + compile lines below.

1. SEMANTICS ARE IDENTICAL, INSTRUCTION SHAPE IS NOT
   The attack (bounds-check -> secret load -> cache-line-strided transmit) is the
   same on all 3, but the instruction count differs by ISA class:
     SPECTRE_V1:  x86  8 instrs |  arm 16 |  riscv 14
   x86 (CISC) folds addressing into the load (movzbl (%rax,%rdi)); arm/riscv (RISC)
   MATERIALIZE every global address explicitly (arm: adrp+ldr+ldr via GOT; riscv:
   lui+ld), inflating instruction and LOAD counts.

2. CANONICAL-OP ABSTRACTION PRESERVES THE CLASS SIGNATURE, NOT THE COUNTS
   V1 canonical-op multiset per ISA:
     x86_64 : BRANCH_COND 1, LOAD 1, SHL 1, STORE 1
     arm64  : BRANCH_COND 1, LOAD 6, SHL 1, STORE 1, ADDR_GEN 3, MOV 1
     riscv64: BRANCH_COND 1, LOAD 3, SHL 1, STORE 1, ADDR_GEN 3, ADD 3, MOV 1
   The discriminative primitives (BRANCH_COND+LOAD+SHL+STORE) survive on ALL 3 --
   but the LOAD count is inflated 3-6x on RISC by addressing overhead.

3. PDG (graph) scales with instruction count: x86 8 nodes, arm 16, riscv 14.

4. CLASSIFIER VERDICT (baseline, size-matched small gadgets):
   SPECTRE_V1 (strong-signal class):
     x86_64  -> SPECTRE_V1 conf 1.00
     arm64   -> SPECTRE_V1 conf 0.67
     riscv64 -> SPECTRE_V1 conf 0.94   <== CORRECT, zero-shot, despite no riscv training
   SPECTRE_V4 (weaker-signal class), same-source 3 ISAs:
     x86_64  (LOAD 4) -> SPECTRE_RSB  conf 0.61  (V4 prob 0.04) WRONG
     arm64   (LOAD 8) -> BENIGN       conf 1.00  (V4 prob 0.00) WRONG
     riscv64 (LOAD 5) -> SPECTRE_V1   conf 0.57  (V4 prob 0.00) WRONG

CONCLUSION -- cross-ISA robustness is a function of CLASS SIGNAL STRENGTH:
- For a WELL-REPRESENTED class (V1), the spec-neutral representation TRANSFERS: the
  same gadget classifies consistently and correctly across all 3 ISAs, even zero-shot
  on riscv, WHEN SIZE-MATCHED. This is WHY windowing the large real riscv PoCs to
  training size recovered them, and why a clean small riscv V1 scores 0.94 at baseline.
- For a WEAKER-SIGNAL class (V4), the ISA-specific addressing overhead (LOAD-count
  inflation on RISC) DOMINATES the weak class signal and pushes the SAME gadget to
  three DIFFERENT wrong labels. The representation does not rescue an under-learned class.

This reconciles the whole RISC-V arc: the representation is ISA-robust; the RISC-V
failure was (a) graph SIZE (large real functions vs small training windows -> H3) and
(b) DATA (no idiomatic per-class riscv training). The fix -- idiomatic riscv training
data per class -- targets exactly (b): it strengthens each class's signal on riscv so
the ISA noise no longer flips the label.

Reproduce: qemu_data/xisa/gadget.c, gadget_v4.c + the clang/riscv64-elf-gcc lines;
eval via v54/viz_v54_spec + spec/eval machinery.

--- LOAD-NORMALIZATION TEST (2026-09-02) ---
Hypothesis: RISC address-materialization loads inflate the LOAD count and
destabilize weak classes cross-ISA (V4 got 3 different labels). Test two normalizers.

(A) NAIVE syntactic (symbol-relative load -> ADDR_GEN): FAILS to align.
    V1 LOAD after: x86 0 / arm 3 / riscv 1  (worse, not aligned)
    Root: two deeper inconsistencies -- (a) x86 byte-load is MOV_ZX (movzbl), NOT
    LOAD; (b) arm's GOT deref is 2 instrs and the second load (ldr [x8]) has no symbol.

(B) DATAFLOW (a DATA-load = memory read whose value is used as data, NOT as a
    subsequent memory base/index): ALIGNS cross-ISA.
      class   raw mem-reads (x86/arm/riscv)   dataflow data-loads
      V1      2 / 6 / 3                        1 / 1 / 1   <- perfectly aligned
      V4      5 / 8 / 5                        1 / 1 / 2   <- nearly (riscv SSB double-deref)
    The RISC addressing overhead (2-6x extra loads) is exactly what the dataflow
    filter removes, leaving the ISA-neutral discriminative load count.

CONCLUSION: load-normalization works, but must be DATAFLOW-based, not syntactic. The
dataflow data-load count is ISA-neutral (V1 1/1/1) where raw counts are inflated
(2/6/3). This is a candidate node/graph FEATURE for cross-ISA robustness that needs
NO extra data -- it strips the ISA-specific noise the V4 study showed flipping labels.
The PDG already carries data-dependence edges, so "a load whose value feeds only
addressing" is computable from the existing DFG.

NEXT (to test the CLASSIFIER effect): add a dataflow data-load feature (or reclassify
address loads to ADDR_GEN via the DFG) and retrain; re-run the V4 cross-ISA test --
does the same gadget then classify consistently across ISAs? Representation aligns;
classifier effect is the retrain follow-up.

--- x86 movz/movs LOAD fix — confirmation retrain (2026-09-02) ---
Fixed: x86 memory-source movz*/movs* now classify LOAD (was MOV_ZX), so the secret
byte-load is LOAD on all 3 ISAs. Touches 48% of x86 train records (feature change).
Confirmation retrain (2 seeds): locked test 95.45 / 96.11 (mean 95.78) vs pre-fix
baseline 95.88 ± 0.43 -> NO regression, within variance. The correctness fix is free.
Cross-ISA base is now consistent (secret load = LOAD everywhere); the dataflow
data-load normalization builds on this next.

--- DATAFLOW DATA-LOAD FEATURE — retrain test (2026-09-02): NEGATIVE, instructive ---
Added two inline features: data_load_count (ISA-neutral, V1 1/1/1) and addr_load_count
(the RISC overhead, V1 0/5/2). Retrained 2 seeds (x86/arm, no riscv), 60-dim.

Result:
  in-distribution locked test: 96.23 / 96.41  (UP from 95.88 baseline -- feature helps x86/arm)
  zero-shot riscv attack:      still 0%        (no help)
  cross-ISA consistency (same gadget, 3 ISAs):
     baseline: V1 CONSISTENT (all 3 -> V1), V4 inconsistent
     dlnorm  : V1 now INCONSISTENT (x86 V1, arm/riscv BENIGN); V4 still inconsistent -> WORSE

CONCLUSION -- the feature-ADDITION approach BACKFIRED. data_load_count aligns
cross-ISA, but pairing it with addr_load_count (ISA-specific by construction) handed
the model a NEW ISA-discriminating shortcut: it learned "high addr_load => arm/riscv
=> different", so V1 (previously ISA-consistent) broke. In-distribution improved
because on x86/arm the addr_load signal is informative -- the classic spurious-
correlation trap (in-distribution up, out-of-distribution down).

Root mistake: ADDING a feature does not REMOVE the ISA signal already in frac_LOAD
(still counts all loads, still RISC-inflated). It ADDS competing ISA signal. The
CORRECT implementation is to RECLASSIFY address-materialization loads -> ADDR_GEN at
the NODE/opcode level (via the DFG), so frac_LOAD itself becomes data-loads-only and
the inflated count is REMOVED, not competed with. That is the real follow-up; the
feature-addition variant is reverted (it hurts the stated cross-ISA goal).

KEPT: the x86 movz/movs -> LOAD correctness fix (separate, committed, +0 regression).

--- NODE-LEVEL RECLASSIFICATION attempt (2026-09-02): needs real DFG, not a heuristic ---
Tried reclassifying address-materialization loads LOAD -> MOVE at the node level (to
REMOVE the inflated load signal, not add a competing feature). Two text heuristics:
  (i)  "dest reg used as a memory base anywhere later" -> WRONG: a transmit gadget's
       SECRET load IS eventually used to form the probe address, so it mis-flags the
       secret load. (V1 node LOAD: x86 0 / arm 1 / riscv 1 -- not aligned)
  (ii) "FIRST use of the dest is a memory operand (pointer) vs ALU (data)" -> still
       mis-aligns (V1 x86 0 / arm 2 / riscv 3), broken by REGISTER-WIDTH ALIASING
       (eax vs rax, w8 vs x8) and by needing to track whether the value passes through
       a shift/ALU transform before addressing.

CONCLUSION: the load-normalization idea is representation-valid (the study showed the
data-load COUNT can align 1/1/1), but a ROBUST implementation needs a proper def-use
dataflow over the PDG's DATA_DEP edges -- using the builder's register model (which
already resolves width aliasing) and a transform-aware rule (secret load = value goes
through an ALU/shift before a memory-address use; pointer load = value used directly
as a base). Text heuristics on raw instructions are too fragile. That is the real
implementation, deferred. Three quick variants (syntactic, feature-add, node-text)
all reverted; only the x86 movz/movs -> LOAD correctness fix is kept.

NET for the cross-ISA thread: representation is ISA-robust for strong classes (V1
transfers, riscv 0.94 zero-shot when size-matched); the x86 byte-load classification
bug is fixed; and load-normalization is scoped to what it actually requires (DFG
def-use), not shipped as a fragile heuristic.
